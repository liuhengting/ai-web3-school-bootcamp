## 笔记 / 问题

> MCP（Model Context Protocol）是 AI 模型与外部工具/资源交互的标准化协议。
> 类似 Web3 中的 RPC，MCP 解决了 AI Agent 调用工具时的接口不统一问题。

---

## MCP 协议笔记

### 核心知识点

**MCP 的本质定位。** MCP 解决的不是"模型更聪明"，而是"模型如何以可描述、可复用、可管理的方式使用外部能力"。它把模型与工具、数据源、应用上下文之间的连接标准化，是 AI 应用的"工具接口标准"。

**架构分工：Client 与 Server。** Server 负责暴露资源、工具和 Prompts，Client 负责连接模型与 Server，发现能力、转发调用请求、处理用户确认和权限提示。判断 Client 是否靠谱，看它是否让用户清楚知道连接了哪些 Server、模型能调用哪些工具、调用前是否需确认。

**Tool Schema 是给模型看的合约。** 好的 Schema 不只是字段类型，还要说明工具的适用场景、参数含义、必填字段、是否有副作用、失败时返回什么。Schema 写得模糊，模型就会用错误参数填空。

**Permission 是最容易被低估的问题。** 至少要区分：只读 vs 写入、会话授权 vs 长期授权、是否需用户确认、是否访问敏感信息、是否产生外部副作用、是否可撤销与审计。MCP 让工具连接更方便，但方便不等于安全。

**MCP vs Shell 权限模型。** Shell 的权限是 OS 级别的"信任操作者"模型（UID/GID + rwx），假设操作者是人，有判断力；MCP 的权限是"不信任调用者"模型，因为调用者是模型，可能误解工具、填错参数或被 prompt 注入诱导。Shell 把语义层安全推给人脑，MCP 试图在协议层消化这些复杂性。

**--help ≠ Tool Schema。** `--help` 是给人看的文档，Tool Schema 是给模型看的合约。前者容忍歧义，后者必须精确约束类型、枚举值、依赖关系和副作用。对常见 Shell 命令，模型靠训练数据中的经验记忆可以"猜对"；面对新工具，没有 Schema 就会高频出错。

### 疑问

1. MCP 的 Permission 模型目前是否有标准化的实现方案，还是各 Server 自行定义？如果各做各的，是否会重蹈"每个应用用自己的方式接工具"的覆辙？
2. 页面提到"MCP 本身不是钱包安全方案"，那么在 AI x Web3 场景下，MCP 与账户抽象、Session Key 等机制的具体协作边界在哪里？
3. 对于已有的 Shell 工具生态，是否存在自动将 `--help` / man page 转化为合格 Tool Schema 的方案？还是必须人工逐个编写？
