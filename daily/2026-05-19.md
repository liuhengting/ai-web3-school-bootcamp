## 笔记 / 问题

> Context 不是简单的长文本拼接，而是一套信息治理问题。你要为每类信息标注来源、时效、权限和可信度。否则模型会把“用户说的”“网页写的”“链上查到的”“系统规定的”混在同一层处理。
> - **可信来源要显式标注**：系统状态、用户输入、检索文档、工具结果要分区放置。
> - **上下文要可刷新**：状态、配置、权限、价格、版本和任务进度不能长期缓存后继续使用。
> - **记忆要可撤销**：用户偏好和历史任务可以提升体验，但不能变成隐藏权限或永久身份假设。

在根据阅读教程和AI的沟通学习过程中，我发现和AI会话过程或者和Agent会话过程中的Context应该分为显式Context和隐式Context：显式Context会包括工具自动携带的系统提示词、用户手动指定的Skill、用户指定的文档或者代码文件、用户的输入等，这种显式能查看到的会话输入；隐式Context主要是就是AI在整个会话过程中动态的记忆滑动窗口。对于Context概念和机制的了解，可以从AI使用者和AI应用开发者两个角度去辅助我们思考，从AI使用者的角度尽量在一个会话过程中维持在一个大主题下，从AI应用开发者的角度尽量把Context的来源和信息量限制在合理的范围内，避免信息过多导致AI的运行效率下降，但是很难限制用户的输入主题，如果是垂直领域的Agent可以通过引导的方式让用户输入限定在某个大主题下。

----

> 一个 RAG 系统至少有三次判断：文档怎么切，查询时取哪些内容，生成时如何引用和拒答。任何一层做错，模型都会拿着错误材料说得很顺。
> - **检索结果不是事实**：它只是候选证据，仍要看来源、时间、版本和适用范围。
> - **引用要能回到原文**：答案里的关键判断应该能追溯到具体文档、段落或链上记录。
> - **检索失败要允许拒答**：找不到证据时，系统应该说“不确定”，而不是让模型补全。

RAG 相对于 Claude Code 为代表的 Agentic Search 看起来是一种更复杂的架构。RAG 相对于Agentic Search就多了预处理流程: 切片、向量化，尤其是在知识库不够大的情况下使用RAG首先启动成本就更高，在知识库不够大或者刚起步的过程中可以考虑先使用Agentic Search，然后等知识库扩大后使用RAG。同时和AI的学习过程中了解到现在企业级的解决方案逐步走向了融合，在大知识库中使用 RAG 定位到具体的几篇文档，然后使用 Agentic Search 获取更准确、更完整的答案。
